# BitTorrent Backend

The BT backend is `LazyBtBackend` (registered as the `TaskKind::Bt` backend) plus
`RqbitBtBackend` (the running engine), and the whole pair now lives in its own
crate, `limedl-bt` — the only crate that names the engine. It is built on
`librqbit` (workspace dependency `9.1`, `default-features = false`,
`rust-tls`); the earlier irontide-based engine was replaced, and migration
removes the old `.resume` files since librqbit persists state as
`session.json`/`<hash>.torrent`/`<hash>.bitv`
[[cite:Cargo.toml:L84-L85]],
[[cite:crates/limedl-bt/src/lib.rs:L1-L36]],
[[cite:crates/limedl-bt/src/lazy.rs:L95-L110]].

## Lazy startup and the restartable engine slot

Creating a librqbit session binds TCP/uTP sockets, starts DHT, loads resume data,
applies rate limits and parses the blocklist. `LazyBtBackend` moves that off the
startup path [[cite:crates/limedl-bt/src/lazy.rs:L1-L27]]:

- `new()` only records the launch configuration — no network, no disk
  [[cite:crates/limedl-bt/src/lazy.rs:L188-L216]].
- `spawn_startup()` kicks off a background warm-up; `bootstrap()` returns without
  waiting [[cite:crates/limedl-bt/src/lazy.rs:L218-L242]].
- Operations that need the engine await `engine()`; `list` and read-only
  peer/tracker/piece/file queries do **not** block (the task list is loaded
  before the desktop window is shown)
  [[cite:crates/limedl-bt/src/lazy.rs:L17-L27]].

The engine slot is `RwLock<Option<Arc<RqbitBtBackend>>>`, not a `OnceCell`, so
the session can be unloaded and rebuilt. Creation and teardown are serialized by
a `lifecycle: tokio::sync::Mutex<()>`, so an idle shutdown in flight and a fresh
`engine()` cannot both bind the listen port
[[cite:crates/limedl-bt/src/lazy.rs:L166-L215]].

A failed start is cached in `startup_error`: later calls fail fast with the
original message instead of silently re-creating a session that holds exclusive
resources. An explicit `spawn_startup()` clears that cache so the user can retry
[[cite:crates/limedl-bt/src/lazy.rs:L42-L46]],
[[cite:crates/limedl-bt/src/lazy.rs:L736-L755]].

`engine()`
[[cite:crates/limedl-bt/src/lazy.rs:L330-L383]]:

1. returns the cached startup error or the shutting-down error;
2. records `last_activity_ms` (so the idle supervisor does not unload between
   returning and the torrent being inserted);
3. returns an already-ready engine;
4. takes the lifecycle guard, re-checks, creates the engine, records a failure;
5. if `shutting_down` was set while the session came up, shuts the late engine
   down and errors;
6. stores the engine, clears `startup_error`, and refreshes+publishes the index
   (restored torrents' `Added` alerts fired before the bridge subscribed).

## Background loops

- `spawn_index_sync_loop()` runs every 5 s (`INDEX_SYNC_INTERVAL`), mirrors the
  engine's `list()` into `bt_tasks`, and self-heals eager mode: if lightweight
  mode was turned off at runtime and no engine is ready with no cached error, it
  starts one [[cite:crates/limedl-bt/src/lazy.rs:L244-L267]].
- `spawn_idle_supervisor()` runs every 10 s, is a no-op unless lightweight mode
  is on, waits out a 20 s idle settle window (`IDLE_SETTLE`), and unloads the
  engine when `has_active_torrents()` is false. "Seeding counts as active", so a
  seeding session stays up. An error from the active check keeps the engine up
  rather than tearing it down
  [[cite:crates/limedl-bt/src/lazy.rs:L269-L311]],
  [[cite:crates/limedl-bt/src/lazy.rs:L79-L93]].

`has_unfinished_tasks()` reads the persisted index and falls back to the on-disk
resume files when the index is empty (first run after enabling lightweight mode,
or an upgrade from a build with no index)
[[cite:crates/limedl-bt/src/lazy.rs:L313-L328]].

## Lightweight mode and the bt_tasks cache

With `bt.lightweight_mode` on, `bootstrap` warms the engine only when
`has_unfinished_tasks()` is true
[[cite:crates/limedl-core/src/bootstrap.rs:L80-L84]]. While the engine is down,
`list()` serves rows from the `bt_tasks` index, clearing volatile metrics
(speed/upload speed/eta/peers/connection count) so the UI does not show a dead
session's old numbers
[[cite:crates/limedl-bt/src/lazy.rs:L716-L730]].

`bt_tasks` is a **cache, not the source of truth**: librqbit's own persistence
is, and a running engine's `list()` overwrites the index. Writes happen when the
engine becomes ready, on the 5 s sync tick, and before unload/shutdown
[[cite:crates/limedl-bt/src/lazy.rs:L694-L714]],
[[cite:crates/limedl-bt/src/lazy.rs:L638-L658]]. The whole table is replaced in
one `BEGIN IMMEDIATE` transaction (delete + reinsert) so a crash cannot leave a
half-updated index; `cancel`/`remove`/`purge` delete rows
[[cite:crates/limedl-bt/src/lazy.rs:L785-L826]],
[[cite:crates/limedl-store/src/database/bt_task_repo.rs:L26-L46]].

## Task identity, snapshots and magnets

A BT task id is the raw info-hash hex string (no `bt:` prefix internally);
`task_map: FastDashMap<Id20, Id20>` is the set of active torrents and
`torrent_created_at` records creation time (set on start, cleaned on
cancel/remove/purge)
[[cite:crates/limedl-bt/src/lib.rs:L96-L127]],
[[cite:crates/limedl-bt/src/snapshot.rs:L48-L56]].
`stats_to_snapshot` maps librqbit `TorrentStats.progress_bytes` to
`downloaded_bytes` (bytes in flight, not only verified pieces) for smooth
progress, takes live speed/peer count from `stats.live`, hides speed in terminal
states, and estimates ETA from total/downloaded/speed
[[cite:crates/limedl-bt/src/snapshot.rs:L11-L78]].

`get_torrent_files()` reads `api_torrent_details()` and takes the `included`
flag per file directly from librqbit's per-file details, with downloaded bytes
from `api_stats_v1().file_progress`; a pending magnet returns an empty list
[[cite:crates/limedl-bt/src/queries.rs:L193-L224]].

Magnet links (and bare 40-char info hashes) are resolved in the background:
`start` reserves the slot and task-map entry immediately, spawns
`session.add_torrent` for the metadata fetch, and tracks the in-flight
resolution in `pending_magnets` with an abort handle (pause/cancel of a pending
magnet flips the flag or aborts the task)
[[cite:crates/limedl-bt/src/lifecycle.rs:L114-L178]],
[[cite:crates/limedl-bt/src/lifecycle.rs:L273-L290]].

## The state monitor bridge is the sole BT notification emitter

librqbit exposes no alert queue here: `setup_alert_bridge()` spawns a state
monitor that polls every 500 ms, diffs each torrent's snapshot state
(unknown/paused/finished/error) against the last-seen state and derives
`BtEvent::Added/Paused/Resumed/Finished/Error`, plus a 2 s progress tick that
emits a `Progress` event for every torrent in `task_map`
[[cite:crates/limedl-bt/src/alerts.rs:L148-L211]].

`handle_event` is the mapping table (extracted so tests can feed synthetic
events) [[cite:crates/limedl-bt/src/alerts.rs:L66-L133]]:

| Event | Emits |
| --- | --- |
| `Added` | `Aria2Notification(onDownloadStart)` + task_map insert |
| `Paused` | `onDownloadPause` + `Updated` |
| `Resumed` | `onDownloadStart` + `Updated` |
| `Finished` | `onDownloadComplete` + `onBtDownloadComplete` + `Updated` + `Progress` |
| `Error` | `onDownloadError` + `Updated` |

Because restored torrents are added *during* session creation — before the
monitor subscribes — `engine()` refreshes and publishes the index explicitly so
restored rows reach the UI without waiting for the first tick
[[cite:crates/limedl-bt/src/lazy.rs:L376-L379]],
[[cite:crates/limedl-bt/src/lazy.rs:L694-L714]]. Lifecycle `Updated` events from
start/cancel/remove/purge are emitted by the Dispatcher, not here, and the
Aria2 RPC handlers broadcast notifications only for HTTP tasks — BT
notifications have exactly this one source
[[cite:crates/limedl-rpc/src/download.rs:L137-L139]].

## Upload policy

`spawn_upload_policy_loop()` runs every 5 s and enforces the user's
whole-torrent limits. When `upload_limit_bytes` or `upload_ratio_limit` is
reached and `pause_upload_when_limit_reached` is set, a **finished (seeding)**
torrent is paused via `session.pause`, tracked in `paused_by_limit`; the flag
(and the pause) is released only when the condition no longer holds, which
avoids per-tick oscillation. With no limits configured the loop clears its state
and skips [[cite:crates/limedl-bt/src/uploads.rs:L41-L92]].

## Anti-leech

`spawn_anti_leech_loop()` runs every 10 s and acts on **individual
under-contributing peers**, independent of the whole-torrent upload policy,
reading per-peer counters via `api_peer_stats`. `peer_is_leecher` is a pure
function [[cite:crates/limedl-bt/src/anti_leech.rs:L56-L105]]:

1. skip upload-only peers and peers with `progress >= 1.0`, peers we are
   choking, and peers within the grace period;
2. signal A: the peer chokes us while we keep sending it data and receive
   essentially nothing;
3. signal B: the give-back ratio is below the threshold
   (`ratio == 0` disables this check).

The implemented action is Ban: an IP is recorded in `banned_leechers` with an
expiry timestamp (so shared NAT/VPN peers are eventually unbanned, swept each
tick), and a `DownloadEvent::Warning` is published
[[cite:crates/limedl-bt/src/anti_leech.rs:L140-L220]]. The `LimitSlots` action
and `anti_leech_max_upload_slots` exist in settings/UI but the current loop does
not cap upload slots, and the ban list is bookkeeping/warning-level — it does
not yet reject connections at the librqbit layer. Disabling the feature clears
the ban and slot state maps
[[cite:crates/limedl-bt/src/anti_leech.rs:L154-L162]],
[[cite:crates/limedl-types/src/types/bt.rs:L80-L84]].

## Engine tuning and blocklist

`RqbitBtBackend::new` translates `BtSettings` into `librqbit::SessionOptions`
at creation: DHT enable/port, TCP-only vs TCP+uTP listener mode, listen
port/port-range, UPnP, IPv4-only, per-torrent peer limit, global
download/upload rate limits, and the blocklist as a `file://`
`blocklist_url`. Fastresume and JSON persistence point at the resume directory;
restored torrents are seeded into `task_map`/`torrent_created_at`
[[cite:crates/limedl-bt/src/session.rs:L34-L125]].

`apply_settings` (hot path) stores the new snapshot, rebuilds the `.torrent`
HTTP client through `build_http_client` (keeping the previous client on failure
rather than silently bypassing the configured proxy) and live-updates the two
rate limits via `session.ratelimits`
[[cite:crates/limedl-bt/src/session.rs:L190-L207]]. Note the reduction from the
irontide era: **the blocklist is applied only at session creation** —
`apply_blocklist` is a stub, and listen-port/DHT/choking changes need a new
session (in lightweight mode the idle unload/reload cycle achieves that
naturally) [[cite:crates/limedl-bt/src/session.rs:L209-L211]].

## Shutdown ordering

`LazyBtBackend::shutdown()`
[[cite:crates/limedl-bt/src/lazy.rs:L471-L501]]:

1. sets `shutting_down` (new work is rejected and a late warm-up tears itself
   down);
2. aborts the index mirror (but leaves the idle supervisor alone so an in-flight
   teardown is not interrupted);
3. waits for the warm-up task, with a 20 s grace timeout
   (`STARTUP_SHUTDOWN_GRACE`);
4. takes the lifecycle guard so any in-flight creation finishes;
5. writes the final index and calls `engine.shutdown()`.

`RqbitBtBackend::shutdown()` then aborts the upload-policy, anti-leech and
state-monitor loops, aborts every pending magnet resolution, and stops the
session
[[cite:crates/limedl-bt/src/session.rs:L155-L188]].
