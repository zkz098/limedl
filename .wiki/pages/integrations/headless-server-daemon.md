# Headless Server Daemon (`limedl-server`)

`crates/limedl-server/` is a workspace member that runs the same engine as the
desktop client with no GUI and exposes the Aria2 JSON-RPC API — served by the
`limedl-rpc` crate it depends on directly — so AriaNg, Motrix and aria2 scripts
can drive it on a NAS, a soft router or a container
[[cite:crates/limedl-server/src/lib.rs:L1-L10]],
[[cite:crates/limedl-server/Cargo.toml:L20-L24]]. It is the second frontend over
the shared `Dispatcher`: `main` is a two-line wrapper around the library
[[cite:crates/limedl-server/src/main.rs:L1-L7]], and the library is deliberately
the testable part [[cite:crates/limedl-server/src/lib.rs:L28-L38]].

## Entry point and startup sequence

`main` is `#[tokio::main]` and calls `main_entry()`, which parses argv into
`Cli`, resolves a `Config`, and runs `run_with(config, shutdown_signal())`
[[cite:crates/limedl-server/src/main.rs:L4-L7]],
[[cite:crates/limedl-server/src/lib.rs:L28-L32]]. `run_with` takes the shutdown
future as a parameter so an integration test can start the daemon without
raising a process signal [[cite:crates/limedl-server/src/lib.rs:L34-L38]].

`run_with` performs, in order [[cite:crates/limedl-server/src/lib.rs:L38-L142]]:

1. create `state_dir` (`<data_dir>/downloads`);
2. install logging from `LogSettings::default()` with the CLI level, so engine
   start-up messages are captured;
3. take the exclusive data-directory instance lock;
4. `bootstrap(state_dir)` — the same call the desktop makes;
5. persist `--download-dir` through `save_settings_with` when given;
6. re-apply the on-disk logging settings (the CLI level still wins);
7. clone `settings.aria2_rpc`, force the daemon's overrides, and build
   `Aria2RpcServer`;
8. spawn `serve` and select on it, the signal future and the shutdown `Notify`;
9. call `core.registry.shutdown_all()`.

## Configuration resolution

| Flag | Effect |
| --- | --- |
| `--data-dir <PATH>` | Base directory; highest precedence [[cite:crates/limedl-server/src/cli.rs:L26-L29]]. |
| `--rpc-listen <ADDR>` | Bind address override (`0.0.0.0` for LAN) [[cite:crates/limedl-server/src/cli.rs:L31-L33]]. |
| `--rpc-port <PORT>` | Port override (aria2 alias `--rpc-listen-port`) [[cite:crates/limedl-server/src/cli.rs:L35-L37]]. |
| `--rpc-secret <TOKEN>` | Forces shared-secret auth; falls back to `$LIMEDL_RPC_SECRET` [[cite:crates/limedl-server/src/cli.rs:L39-L42]]. |
| `--rpc-allow-origin-all` | Sets `allow_any_origin` [[cite:crates/limedl-server/src/cli.rs:L44-L47]]. |
| `--rpc-allow-origin <ORIGIN>` | Appends a specific CORS origin (repeatable) [[cite:crates/limedl-server/src/cli.rs:L49-L51]]. |
| `--download-dir <PATH>` | Must be absolute; persisted (aria2 alias `--dir`) [[cite:crates/limedl-server/src/cli.rs:L53-L57]]. |
| `--log-level <LEVEL>` | `trace`/`debug`/`info`/`warn`/`error`, mapped from a local `LogLevelArg` enum because `limedl-core` does not depend on `clap` [[cite:crates/limedl-server/src/cli.rs:L64-L85]]. |

Every flag overrides `settings.json` for that run only, except
`--download-dir`, which is persisted [[cite:crates/limedl-server/src/cli.rs:L1-L7]].
The data directory follows the desktop's precedence: `--data-dir`, then
`$LIMEDL_DATA_DIR`, then the platform local data dir, then a temp fallback
[[cite:crates/limedl-server/src/config.rs:L1-L9]],
[[cite:crates/limedl-server/src/config.rs:L88-L99]]; `state_dir` is always
`<data_dir>/downloads`, matching `SystemContext`'s rule that `settings.json` is
the parent of the state directory [[cite:crates/limedl-server/src/config.rs:L30-L43]].
The secret is read from `$LIMEDL_RPC_SECRET` when the flag is absent, which
keeps it out of the process list
[[cite:crates/limedl-server/src/config.rs:L55-L60]].

## The daemon's RPC overrides

The daemon differs from the desktop in exactly three ways, applied in `run_with`
[[cite:crates/limedl-server/src/lib.rs:L85-L104]]:

- `enabled = true` — the RPC endpoint is the daemon's only interface, so it does
  not honour `settings.json`'s disabled default
  [[cite:crates/limedl-server/src/lib.rs:L86-L87]];
- `exit_on_shutdown = true` — `aria2.shutdown` stops the process (aria2
  semantics), where the desktop keeps it off because the UI owns exit
  [[cite:crates/limedl-server/src/lib.rs:L88-L90]];
- CLI overrides for `listen_address`, `port`, `secret` (which also forces
  `Aria2AuthMode::Single`), `allow_any_origin` and additional CORS origins
  [[cite:crates/limedl-server/src/lib.rs:L91-L102]].

It then relies on the core server's fail-closed gate: a non-loopback
`listen_address` without authentication makes `serve` return an error, which
propagates as the daemon's startup failure rather than silently exposing an
anonymous endpoint [[cite:crates/limedl-rpc/src/server.rs:L177-L183]],
[[cite:crates/limedl-rpc/src/server.rs:L56-L73]].
`Aria2RpcServer::shutdown_notify()` is cloned out before `serve` consumes the
server so the `aria2.shutdown` notification can be awaited
[[cite:crates/limedl-server/src/lib.rs:L104-L105]].

## No host power management

The daemon stores `settings.json` verbatim — including the desktop's
`power.preventSleep` — but nothing in the server acts on it: the crate declares
no power-related dependency and contains no power API call at all. That is a
deliberate boundary rather than a missing feature
[[cite:crates/limedl-server/Cargo.toml:L20-L30]],
[[cite:docs/server-daemon.md:L227-L231]]:

- In the container image the daemon is the *guest*. `org.freedesktop.login1`
  belongs to the host's system bus, and whether the host may suspend is the host
  operator's decision, not a download client's
  [[cite:docs/server-daemon.md:L227-L229]].
- A NAS or 软路由 exists to stay up and serve; a keep-awake lock there would mask
  a host misconfiguration instead of fixing it
  [[cite:docs/server-daemon.md:L227-L231]].

Operators who need the host to stay awake while the queue runs arrange it on the
host — pause the queue, or disable idle suspend there; only `limedl-native` acts
on `power.preventSleep` [[cite:docs/server-daemon.md:L229-L231]]. The desktop
client's implementation of the same setting is described in
[[wiki:desktop/native-ui-architecture]].

## Instance lock

Two daemons pointed at one data directory would race on the SQLite database, the
torrent state and the RPC port. `acquire_instance_lock` creates
`<data_dir>/limedl-server.lock` and calls `File::try_lock`; a second instance
fails with an explanatory error. The lock is held for the process lifetime and
released by the OS on exit, so a crash does not leave a stale lock
[[cite:crates/limedl-server/src/lib.rs:L144-L166]],
[[cite:crates/limedl-server/src/lib.rs:L58-L60]]. Its exclusivity is pinned by
the `instance_lock_is_exclusive_and_reusable` unit test
[[cite:crates/limedl-server/src/lib.rs:L198-L213]].

This guards against a second *daemon* only. It does not make a desktop client
safe to run against the same data directory; that is why `docs/server-daemon.md`
tells operators to stop one before starting the other
[[cite:docs/server-daemon.md:L213-L216]].

## Shutdown and signals

`run_with` spawns `serve` as a task, then `tokio::select!`s on
[[cite:crates/limedl-server/src/lib.rs:L110-L126]]:

- the injected shutdown future (`main_entry` passes `shutdown_signal`),
- the `shutdown_notify` handle that `aria2.shutdown` fires, and
- the `serve` task itself, so a bind error propagates instead of hanging.

Whichever wins, the daemon sends `true` on the server's `watch` channel (when a
shutdown was requested), awaits the serve task, and then calls
`registry.shutdown_all()` to flush manifests, checkpoint the WAL and release the
BT session [[cite:crates/limedl-server/src/lib.rs:L127-L141]]. `shutdown_signal`
is `SIGTERM`/`SIGINT` on Unix and `ctrl_c` on non-Unix, mirroring the desktop's
signal watcher but without the Slint event loop
[[cite:crates/limedl-server/src/lib.rs:L168-L192]].

## Packaging and deployment

The crate has no Slint, tray or dialog dependency — only `limedl-core`,
`limedl-rpc`, `clap`, `tokio`, `anyhow` and `tracing` — so it cross-compiles to
a fully static musl binary
[[cite:crates/limedl-server/Cargo.toml:L20-L30]],
[[cite:.github/workflows/release.yml:L533-L538]]. The release pipeline's
`build-server` job builds `x86_64-unknown-linux-musl` and
`aarch64-unknown-linux-musl` with `cargo zigbuild` (zig bundles the musl C
toolchain `aws-lc-sys` needs, without Docker) and uploads tarballs that also
contain the systemd unit and env example
[[cite:.github/workflows/release.yml:L539-L546]],
[[cite:.github/workflows/release.yml:L559-L564]],
[[cite:.github/workflows/release.yml:L597-L612]]. Both targets were verified
locally to produce stripped, statically-linked binaries
[[cite:.github/workflows/release.yml:L543-L544]]. `.cargo/config.toml` already
carries both musl targets, with the x86_64 entry at `target-cpu=x86-64-v2` for
older NAS CPUs [[cite:.cargo/config.toml:L36-L42]].

The daemon also ships as a multi-arch `ghcr.io/zkz098/limedl-server` image that
the `server-image` job assembles from those same prebuilt binaries — it does not
rebuild the engine [[cite:.github/workflows/release.yml:L631-L647]]. The
committed deployment assets (`packaging/server/`) and their install procedure are
documented on [[wiki:operations/server-deployment-and-packaging]], with
operational guidance (systemd, reverse-proxy TLS, security trade-offs) in
`docs/server-daemon.md` [[cite:docs/server-daemon.md:L213-L216]].

## Testing

Pure unit tests cover CLI parsing, `LogLevelArg` → `LogLevel` mapping, config
precedence/trimming, absolute-path validation, the loopback data-dir override
and the instance lock's exclusivity
[[cite:crates/limedl-server/src/cli.rs:L91-L155]],
[[cite:crates/limedl-server/src/config.rs:L125-L193]],
[[cite:crates/limedl-server/src/lib.rs:L198-L213]].

The end-to-end test in `tests/daemon.rs` is the one that proves the wiring: it
starts a real daemon against a temp data directory on a reserved port, polls
`aria2.getVersion` until the engine is up, asserts a missing token is rejected,
calls `aria2.shutdown`, and awaits the daemon task exiting cleanly
[[cite:crates/limedl-server/tests/daemon.rs:L54-L129]]. The readiness poll uses
a fallible `rpc_try` and treats a refused connection as "not ready yet", because
the engine bootstraps and binds the port asynchronously — only the request after
readiness may panic [[cite:crates/limedl-server/tests/daemon.rs:L24-L52]]. It
runs in the Linux `check-rust` job; the Windows/macOS legs only compile the
crate via the workspace clippy [[cite:.github/workflows/ci.yml:L596-L603]].
