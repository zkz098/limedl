# Self-Update and Distribution Channels

The desktop client updates itself in-app through a manifest dual-signed with
Minisign (Ed25519) and ML-DSA-65 (FIPS 204 post-quantum). The implementation
lives in `crates/limedl-native/src/update/mod.rs`, whose header comment lays
out the three channels and the trust chain; the release tooling is in `xtask/`,
and the release workflow in `.github/workflows/release.yml`.
[[cite:crates/limedl-native/src/update/mod.rs:L1-L31]]
[[cite:.github/workflows/release.yml:L1-L15]]

## Install-channel detection

`detect_install_kind()` runs once at startup and checks, in order:
[[cite:crates/limedl-native/src/update/mod.rs:L193-L209]]

1. Windows package identity (`Package::Current()`) → `Store` (MSIX / Microsoft
   Store). Registry `Run` and other per-machine state are virtualized in MSIX.
   [[cite:crates/limedl-native/src/update/mod.rs:L181-L185]]
   [[cite:crates/limedl-native/src/autostart.rs:L1-L6]]
2. The HKCU `...\Uninstall\limedl-native` key → `Installer` (written by NSIS).
   [[cite:crates/limedl-native/src/update/mod.rs:L211-L216]]
3. Otherwise → `Portable`.

On non-Windows platforms it always reports `Portable`. The detected kind drives
both the update path and the UI copy (it is passed into `UiBootInputs` at
boot). [[cite:crates/limedl-native/src/update/mod.rs:L193-L209]]
[[cite:crates/limedl-native/src/main.rs:L158-L167]]

## Manifest identity and channel keys

The release repo is `zkz098/limedl` and the manifest is fetched from the
permanently named URL `.../releases/latest/download/latest-native.json` with
its sidecars `.sig` / `.pqc.sig`; the artifact URLs are `browser_download_url`
style, so no `api.github.com` quota is consumed. GitHub excludes drafts and
prereleases from `latest`, so stable users never see rc/alpha builds.
[[cite:crates/limedl-native/src/update/mod.rs:L62-L74]]
[[cite:crates/limedl-native/src/update/mod.rs:L14-L17]]

The client trusts two embedded public keys in `update/mod.rs`: `PUBKEY_B64`
(minisign/Ed25519, always enforced) and `PQC_PUBKEY_B64` (ML-DSA-65, enforced
whenever it is non-empty). Downloads are capped at `MAX_UPDATE_BYTES`
(512 MiB) and the classical manifest signature is mandatory — a missing `.sig`
aborts the check rather than trusting the JSON.
[[cite:crates/limedl-native/src/update/mod.rs:L43-L78]]
[[cite:crates/limedl-native/src/update/mod.rs:L315-L340]]

Keys are `{os}-{arch}` with macOS spelled `darwin`, and `-portable` is appended
for the portable (and Store) channel:

| Kind | Key |
| --- | --- |
| Windows installer | `windows-x86_64` |
| Windows portable | `windows-x86_64-portable` |
| macOS portable | `darwin-aarch64-portable` |
| Linux portable | `linux-x86_64-portable` |

[[cite:crates/limedl-native/src/update/mod.rs:L218-L238]]
[[cite:.github/workflows/release.yml:L798-L808]]

## Check flow

`check_for_update(settings)` refuses to run for Store installs (the OS owns
that channel), then compares `manifest.version` against the compiled
`CARGO_PKG_VERSION` and returns `None` when not newer; if the platform has no
assets at all it returns `None` ("no update") rather than an error, but if the
platform exists and only this channel is missing it errors with the available
keys; finally it validates the asset `kind` against the channel.
[[cite:crates/limedl-native/src/update/mod.rs:L242-L307]]
The manifest is fetched and **verified before parsing** — a tampered or
truncated manifest is rejected without ever influencing a download URL.
[[cite:crates/limedl-native/src/update/mod.rs:L309-L340]]

`validate_asset_url` is defence in depth on top of the signature: it requires
the `https://github.com/zkz098/limedl/releases/download/v{version}/` prefix and
a short, plain file name, so a manifest bug or fork cannot point the updater at
unrelated bytes. [[cite:crates/limedl-native/src/update/mod.rs:L135-L155]]

The update HTTP client goes through limedl-core's `configure_client_builder`,
so `settings.proxy` applies to update checks and downloads exactly as it does
to downloads; only the User-Agent is overridden to `limedl-native/<version>`.
[[cite:crates/limedl-native/src/update/mod.rs:L367-L384]]

## Installing a verified update

`install_verified(update, verified_file)` routes by the detected kind:
[[cite:crates/limedl-native/src/update/mod.rs:L473-L480]]

- **Store** → error; the Microsoft Store channel is handled by `update::store`,
  which uses `StoreContext::GetDefault` and must run on the UI thread (it
  associates with the window and fails off-thread).
  [[cite:crates/limedl-native/src/update/mod.rs:L856-L883]]
- **Installer** (Windows NSIS) → spawn `setup.exe /P /R` (passive, restart) and
  return `InstallerLaunched`; the handler then exits so NSIS can replace the
  binary. [[cite:crates/limedl-native/src/update/mod.rs:L482-L490]]
  [[cite:crates/limedl-native/src/handlers/updater.rs:L271-L279]]
- **Portable** → `extract_executable` then `self_replace::self_replace` in
  place, returning `ReplacedRestartPending`.
  [[cite:crates/limedl-native/src/update/mod.rs:L497-L536]]

Portable specifics:

- Linux refuses when running inside an AppImage (`APPIMAGE` env var set),
  because the mounted bundle cannot be replaced in place; the user downloads
  the new `.AppImage` directly. [[cite:crates/limedl-native/src/update/mod.rs:L502-L508]]
- macOS re-signs the containing `.app` ad-hoc after replacement
  (`codesign --force --sign -`), because replacing the executable invalidates
  the bundle signature and macOS would refuse to launch it. A plain tarball
  binary has no bundle and skips this.
  [[cite:crates/limedl-native/src/update/mod.rs:L524-L569]]
- Replacement failure is wrapped with an explanation that the install location
  may not be user-writable (`/Applications`).
  [[cite:crates/limedl-native/src/update/mod.rs:L516-L523]]
- `extract_executable` matches tar members by file name (the nested macOS
  `limedl.app/Contents/MacOS/limedl-native` member and the plain
  `limedl-native` both work; Windows takes the first `*.exe` of the zip). On
  Unix the extracted binary gets mode `0o700` (owner-only), since it lives in
  the per-user update work dir and replaces the running process.
  [[cite:crates/limedl-native/src/update/mod.rs:L571-L613]]
  [[cite:crates/limedl-native/src/update/mod.rs:L615-L643]]

## Background checks

The About tab's update card is driven by the `UpdateState` phase machine
(`idle` seeded at boot; handlers move it through `checking`, `up-to-date`,
`available`, `downloading`, `ready` and `error`; the installer path ends with
the process exiting).
[[cite:crates/limedl-native/src/ui_boot.rs:L123-L135]]
[[cite:crates/limedl-native/src/handlers/updater.rs:L227-L285]]
It is scheduled from `handlers/updater.rs`:

- a silent background check runs **45 s after startup**, so a proxy change made
  at startup is already in effect, and
- it is throttled to **once per 24 h** by the `update-check.stamp` file in the
  base directory. A stamp from the future (clock rolled back) is treated as
  fresh. [[cite:crates/limedl-native/src/handlers/updater.rs:L287-L301]]
  [[cite:crates/limedl-native/src/update/mod.rs:L673-L695]]

Store installs skip the silent check entirely. On finding an update the handler
pushes an `available` state and, when notifications are enabled, an OS
notification. [[cite:crates/limedl-native/src/handlers/updater.rs:L289-L331]]

## The signing chain

Every release artifact and the manifest are **dual-signed**: Minisign
(Ed25519) and ML-DSA-65 (FIPS 204 post-quantum). `cargo xtask sign <files>`
writes `<file>.sig` (minisign) and, when the PQC key is configured,
`<file>.pqc.sig` (ML-DSA-65); `cargo xtask manifest` inlines both into the
manifest as the asset's `signature` and `pqcSignature`.
[[cite:xtask/src/main.rs:L110-L120]]
[[cite:.github/workflows/release.yml:L785-L790]]

| Layer | Signed by | Verified by |
| --- | --- | --- |
| `latest-native.json` | `cargo xtask sign` → `.sig` + `.pqc.sig` | `verify_signature_text` before parsing, then `verify_pqc_signature_text` |
| each artifact | `cargo xtask sign` → `<file>.sig` + `<file>.pqc.sig`, inlined as `signature`/`pqcSignature` | sha256 (when present), `verify_signature`, then `verify_pqc_signature` over the exact downloaded bytes |

[[cite:crates/limedl-native/src/update/mod.rs:L309-L340]]
[[cite:crates/limedl-native/src/update/mod.rs:L386-L471]]

ML-DSA-65 signatures are domain-separated by context (`limedl-manifest` for
the manifest, `limedl-artifact` for binaries).
[[cite:xtask/src/main.rs:L65-L69]]
[[cite:crates/limedl-native/src/update/mod.rs:L748-L770]]
The classical Minisign signature is always mandatory (a missing `.sig` aborts);
the PQC check is enforced whenever `PQC_PUBKEY_B64` is non-empty, but if the
`.pqc.sig` sidecar or the asset's `pqcSignature` field is missing the client
logs a warning and accepts the classical-only verification.
[[cite:crates/limedl-native/src/update/mod.rs:L324-L337]]
[[cite:crates/limedl-native/src/update/mod.rs:L460-L468]]

`cargo xtask guard <files>` is the release safety net: it derives both public
keys from the CI secrets (`LIMEDL_SIGNING_KEY`, `LIMEDL_PQC_SIGNING_KEY`),
asserts each equals the corresponding constant (`PUBKEY_B64`,
`PQC_PUBKEY_B64`) embedded in the client, then re-verifies every produced
signature — a rotated secret with a stale constant would otherwise ship a
client that rejects every future update.
[[cite:docs/update-signing-key.md:L16-L27]]
[[cite:.github/workflows/release.yml:L785-L790]]
There is **no key-rollover chain**, so new keys must be rotated into the
constants *before* the first release that ships them; `cargo xtask generate-key`
emits both keypairs and prints the exact `gh secret set` commands, and the
manual `sign-check` workflow proves the round-trip without publishing.
[[cite:docs/update-signing-key.md:L29-L59]]

## The release pipeline

`.github/workflows/release.yml` is tag-triggered (`v*`):
[[cite:.github/workflows/release.yml:L32-L34]]

- `font` fetches the MiSans VF font once and hands it to every desktop build leg
  as the `misans-vf` artifact. [[cite:.github/workflows/release.yml:L50-L67]]
- `changelog` generates the release body with git-cliff from Conventional
  Commits between the previous tag and the released tag.
  [[cite:.github/workflows/release.yml:L74-L112]]
- `build-native` (Windows) produces the portable zip, NSIS setup exe and MSIX.
  [[cite:.github/workflows/release.yml:L123-L132]]
- `build-native-macos` produces the ad-hoc-signed `.app` tar.gz.
  [[cite:.github/workflows/release.yml:L332-L335]]
- `build-native-linux` builds with `cargo zigbuild --target
  x86_64-unknown-linux-gnu.2.17` and produces the portable tar.gz, `.deb` and
  AppImage; a `check-glibc-floor.sh` step fails the leg if the binary's glibc
  symbol floor rises above 2.17.
  [[cite:.github/workflows/release.yml:L400-L420]]
  [[cite:.github/workflows/release.yml:L474-L482]]
- `build-server` cross-compiles the headless `limedl-server` for
  `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` with
  `cargo zigbuild` (zig supplies the musl C toolchain `aws-lc-sys` needs) and
  uploads tarballs that also contain the systemd unit and env example. These
  are **plain release assets**: they never enter `latest-native.json` (whose
  asset map only lists desktop artifacts), because the daemon has no
  self-updater. [[cite:.github/workflows/release.yml:L533-L556]]
  [[cite:.github/workflows/release.yml:L605-L615]]
- `server-image` assembles those prebuilt static binaries into a thin image,
  pushes one image per architecture, and merges them into a multi-arch
  `ghcr.io/zkz098/limedl-server` manifest (the `latest` tag is skipped for an
  alpha/beta/rc). It does not rebuild the engine; QEMU only runs the image's
  Alpine `apk add` layer.
  [[cite:.github/workflows/release.yml:L640-L647]]
  [[cite:.github/workflows/release.yml:L683-L719]]

Both zig-based legs (`build-native-linux`, `build-server`) install the pinned
`ziglang==0.16.0` wheel with `pip --only-binary ":all:"` and symlink its `zig`
onto `PATH`, because the PyPI wheel ships no `zig` console script for
`cargo-zigbuild` to find.
[[cite:.github/workflows/release.yml:L460-L471]]
[[cite:.github/workflows/release.yml:L584-L595]]

`native-manifest` is the **sole writer** of `latest-native.json`. It runs on
`windows-latest` with `if: always()`, downloads only the artifacts whose
platform leg succeeded, builds the asset map from what actually exists, signs
each artifact with both keys, generates the manifest with `cargo xtask
manifest`, signs the manifest, then runs `cargo xtask guard` over all of it.
[[cite:.github/workflows/release.yml:L725-L743]]
[[cite:.github/workflows/release.yml:L764-L854]]
A missing platform key is reported by the client as "no update" instead of an
error, which is why a partial release still updates the platforms that did
build. [[cite:.github/workflows/release.yml:L730-L733]]
[[cite:crates/limedl-native/src/update/mod.rs:L262-L282]]
The `/P /R` NSIS flags and the `SilentInstall normal` directive keep the
installer usable silently and interactively.
[[cite:crates/limedl-native/src/update/mod.rs:L482-L490]]
[[cite:installer/limedl-native.nsi:L55-L61]]

`native-manifest` also lists `build-server` in its `needs`. That is a sequencing
constraint rather than a dependency: every job uploads to the same GitHub
release with the same computed `prerelease` flag, and `native-manifest`
deliberately flips it to `false` last, so a still-running server leg could
otherwise reset the flag from its own upload.
[[cite:.github/workflows/release.yml:L735-L742]]
[[cite:.github/workflows/release.yml:L860-L879]]

The manifest generator is platform-agnostic: it accepts an `--assets-json` map
of `key → { kind, path }`, validates the kind, that each artifact and its `.sig`
exist (and folds in `.pqc.sig` when present), and preserves the asset-map order
in the emitted JSON. `cargo xtask manifest` is therefore reusable for a new
platform matrix leg without code changes.
[[cite:xtask/src/manifest.rs:L110-L176]]
[[cite:xtask/src/manifest.rs:L178-L224]]

## Platform caveats

- **macOS** releases are ad-hoc signed and not notarized; a browser download
  carries `com.apple.quarantine` and needs right-click → Open once. Adding a
  Developer ID later means setting `SIGN_IDENTITY` in `scripts/package-macos.sh`
  plus a notarytool step; no client change is needed.
  [[cite:scripts/package-macos.sh:L15-L26]]
- **Linux** targets `x86_64-unknown-linux-gnu.2.17` with `target-cpu=x86-64-v3`,
  so it needs glibc ≥ 2.17 (Debian 10 / Ubuntu 18.04 / CentOS 7) and a 2013+
  CPU. The `.2.17` suffix is cargo-zigbuild's glibc-version target: the binary
  still links the distro's fontconfig and `dlopen`s X11/Wayland/GL, but its own
  libc references resolve against 2.17 instead of the runner's 2.39.
  [[cite:.github/workflows/release.yml:L400-L411]]
  [[cite:.cargo/config.toml:L10-L18]]
- **MSIX autostart** cannot carry `--hidden` (the manifest's `startupTask` takes
  no arguments), so the client infers a login launch by comparing process
  creation time against the shell's within a 150 s window when package identity
  is present and autostart is enabled.
  [[cite:packaging/msix/AppxManifest.xml:L52-L68]]
  [[cite:crates/limedl-native/src/main.rs:L274-L284]]
  [[cite:crates/limedl-native/src/ui_sync.rs:L131-L133]]
- **`update::clean_update_work_dir`** clears leftover files from a previous
  (possibly interrupted) update at every startup.
  [[cite:crates/limedl-native/src/update/mod.rs:L657-L671]]
  [[cite:crates/limedl-native/src/main.rs:L80-L86]]
