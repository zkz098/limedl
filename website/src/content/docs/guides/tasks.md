# 任务管理与并发策略

limedl 摒弃了传统下载器简单盲目设置固定连接数（如粗暴指定 16 或 32 线程）的做法，而是借鉴现代网络拥塞控制理论，设计了高内聚的 **AIMD（Additive Increase Multiplicative Decrease）自适应并发调度引擎**。

---

## 创建下载任务的多种方式

在桌面端日常使用中，你可以通过以下便捷方式快速发起下载：

1. **智能剪贴板监听**：
   复制有效的 HTTP/HTTPS URL 或 `magnet:?xt=urn:btih:` 磁力链接后，切换至 limedl 窗口会自动弹出新建确认框，自动解析文件名与链接类型。
2. **工具栏点击与快捷键**：
   点击主界面顶部工具栏的 **`+ 新建任务`** 按钮，或在主窗口按下 `Ctrl + N`（macOS 上为 `Cmd + N`），粘贴链接并设置目标存储目录。
3. **拖拽导入种子**：
   直接将本地的 `.torrent` 种子文件拖拽入 limedl 窗口任意位置，即可自动解析种子目录树并展示文件选择列表。
4. **浏览器插件一键接管**：
   配合 Chrome / Edge 上的 Aria2 扩展，在网页中点击任何下载链接，浏览器会自动将请求派发至 limedl。
5. **系统命令行调用**：
   通过终端执行 `limedl-native <URL>`，由单实例机制秒级派发至正在运行的主窗口中。

## HTTP 动态分块引擎工作流程

一个 HTTP 下载任务在 limedl 内部经历严密的五个执行阶段：

```
┌─────────────────┐      HEAD / Range:0-0       ┌───────────────────┐
│ 1. 探测元数据   │ ──────────────────────────► │ 提取 ETag/大小/断点│
└────────┬────────┘                             └─────────┬─────────┘
         │                                                │
         ▼                                                ▼
┌─────────────────┐      根据总大小切片          ┌───────────────────┐
│ 2. 规划 Chunk   │ ──────────────────────────► │ 写入 SQLite 任务库│
└────────┬────────┘                             └─────────┬─────────┘
         │                                                │
         ▼                                                ▼
┌─────────────────┐      JoinSet 异步协程池     ┌───────────────────┐
│ 3. 多流并发拉取 │ ◄─────────────────────────► │ AIMD 动态调速循环 │
└────────┬────────┘                             └─────────┬─────────┘
         │                                                │
         ▼                                                ▼
┌─────────────────┐      落盘缓冲/写合并         ┌───────────────────┐
│ 4. 缓冲池刷盘   │ ──────────────────────────► │ BufferPool 批处理 │
└────────┬────────┘                             └─────────┬─────────┘
         │                                                │
         ▼                                                ▼
┌─────────────────┐      Blake3/SHA-256 哈希    ┌───────────────────┐
│ 5. 校验与最终化 │ ──────────────────────────► │ 原子 Rename 交付  │
└─────────────────┘                             └───────────────────┘
```

### 阶段 1：智能元数据探测 (Probe Phase)
当提交下载链接时，引擎首先向目标 URL 发送轻量级的 `HEAD` 请求（若服务端不支持 HEAD，则平滑回退至 `GET Range: bytes=0-0` 请求）：
- 检测服务端是否支持断点续传（`Accept-Ranges: bytes`）；
- 获取资源总长度（`Content-Length`）；
- 记录资源校验实体标识（`ETag` 与 `Last-Modified`），用于断点续传一致性核验；
- 从 `Content-Disposition` 响应头或 URL 路径中推导并净化目标文件名。

### 阶段 2：动态分块规划 (Chunk Planning)
若服务端支持 Range 请求且文件大于分块阈值，引擎将把文件切分为多个虚拟块（Chunk）：
- **小文件**：采用单流下载并保留断点续传能力；
- **大文件**：根据总长度动态计算最优块尺寸（通常在 2MB ~ 8MB 之间），并构建 `ChunkManifest` 持久化入本地 SQLite 数据库。即使遭遇意外断电，已完成的分块绝不会丢失。

### 阶段 3：AIMD 动态并发调度 (Adaptive Concurrency)
传统固定线程下载有两大弊端：线程过多容易遭遇服务端封禁或触发反爬，线程过少则无法跑满高带宽。

limedl 引入了 **AIMD（加法递增、乘法递减）算法状态机**：
- **加法探测 (Additive Increase)**：
  调度器每隔固定周期（2秒）采样各连接的传输速率与分块完成耗时。若连续几个周期吞吐量保持平稳增长且无连接报错，调度器会逐步向任务追加并发工作连接（+1, +2...），直到达到带宽饱和点。
- **乘法退避 (Multiplicative Decrease)**：
  一旦检测到服务端响应 HTTP 429 (Too Many Requests)、HTTP 503、连接重置或分块读取超时，状态机立即判定为网络拥塞或服务端限流，**瞬间将活动工作线程乘法减半（×0.5）** 并进入冷却期，避免触发服务端永久封禁 IP。
- **镜像故障转移 (Mirror Failover)**：
  当用户为任务配置了多个备用镜像源时，若当前连接源频繁超时，引擎会自动将待下载分块路由至备用镜像，保障下载不掉线。

## 调度模式与并发预算

limedl 提供两种截然不同的调度模式（在 **设置 -> 下载与调度** 中切换）：

### 智能自适应调度 (Automatic Mode) — 默认推荐
- **算法核心**：按**剩余未下载字节数（Remaining Bytes）**结合任务优先级动态重权分配。
- **优势**：大文件优先获得更多线程预算以缩短总体等待时间，多个并发任务间按需动态抢占，最大化利用带宽，无需用户繁琐微调。

### 传统队列调度 (Traditional Mode)
- **算法核心**：严格的 FIFO（先入先出）队列。
- **逻辑**：仅允许最多 `max_parallel_tasks` 个任务处于活跃状态，超出上限的任务在队列中等待。当前一个任务彻底完成后，下一个任务才被依次唤醒。

## 任务优先级系统

在任务列表或右键菜单中，你可以为任意任务指定优先级：

| 优先级等级 | 调度权重倍数 | 适用场景 |
| :--- | :--- | :--- |
| **高 (High)** | 2.0x 线程配额偏好 | 急需使用的重要文件、驱动或镜像，在并发中优先获得连接分配。 |
| **正常 (Normal)** | 1.0x 基准配额 | 默认优先级，各任务按算法平等竞争带宽。 |
| **低 (Low)** | 0.5x 配额限制 | 挂机下载的次要资源，在高峰期主动礼让高优先级任务。 |

## 极速滑动窗口速率采样 (SpeedTracker)

limedl 的任务速率监控基于高精度的滑动时间窗口采样器（`SpeedTracker`）：
- 消除瞬时抖动对界面 UI 的剧烈干扰，提供平滑且真实的实时传输速率。
- 动态加权计算精确的预计剩余完成时间（ETA），告别传统计算方式中忽长忽短的估算跳跃。

## 校验和校验与分块级自愈 (Chunk-level Repair)

limedl 原生支持多种工业级散列算法：
- **Blake3**：极速密码学级校验，单核性能远超 SHA-256 数倍。
- **SHA-256**：广泛通用的标准哈希。
- **XXH3-128**：极致速度的非密码学哈希，适合本地数据快速完整性排查。

### 分块级精准自愈机制
在传统下载器中，若下载完毕后发现 10GB 文件的 SHA256 校验失败，用户通常只能无奈地重新下载整个 10GB 文件。

而在 limedl 中：
1. 引擎在下载各分块时会持续计算并记录每个分块的中间哈希；
2. 一旦全局校验不匹配，校验器会自动精确定位到发生位翻转或数据错乱的**具体坏块**；
3. 引擎**仅将受影响的分块标记为待重试**并重新拉取，在数秒内即可完成文件的无损自愈修复！
