# Slint UI Testing

The desktop UI is tested at two layers, chosen by what regression you want to
catch: **L1** in-process tests that run in the normal `cargo nextest` gate (which
`cargo xtask gate` mirrors), and **L2** the MCP server for interactive inspection
of a running app. [[cite:AGENTS.md:L15-L16]] [[cite:AGENTS.md:L121-L126]]

## L1: in-process tests

`crates/limedl-native/src/ui_tests/` builds the **real** `MainWindow` through
`crate::ui_boot::build_ui` and drives it with Slint's testing backend: element
queries by `.slint` id, simulated clicks, key presses, no window and no display.
`bridge/` unit tests cover the mapping and the state machine; these tests cover
the wiring between them — a callback bound to the wrong handler, a dialog reading
a property nobody sets, or the blast radius of a destructive button.
[[cite:crates/limedl-native/src/ui_tests/mod.rs:L1-L33]]

### The platform is per thread; the event loop is per process

Two testing-backend flavors exist and are incompatible by construction:

- `init_no_event_loop()` installs a mock platform with mock time and **no**
  event-loop proxy. The Slint context is a thread-local, so it is installed once
  **per thread** (`PLATFORM_READY`) and many tests share a process; queued
  `invoke_from_event_loop` callbacks are dropped there.
- `init_integration_test_with_mock_time()` adds the event-loop proxy that
  `pump_until` drains. That proxy lives in a **global** `OnceCell`, so exactly
  one test per process may install it; `EVENT_LOOP_PLATFORM_TAKEN` panics on a
  second attempt.

[[cite:crates/limedl-native/src/ui_tests/mod.rs:L71-L122]]

### Fixture selection

| Fixture | Use |
| --- | --- |
| `with_ui` | default settings, synchronous body |
| `with_settings` | a window seeded from specific `AppSettings` |
| `with_language(Language::EnUs, …)` | the same window with the English catalog (wider labels) |
| `with_ui_async` + `new_window` | contracts that settle on spawned work/timers |

`with_ui`/`with_settings`/`with_language` enter a current-thread tokio runtime
with `enter()` but never drive it: `tokio::spawn` is legal (handlers fire and
forget) but the task is not polled, so assertions must be synchronous — timers
do not fire and `invoke_from_event_loop` delivers nothing. `with_language`
applies the catalog through `slint::select_bundled_translation`, so `@tr`
strings really switch; that selection is process-global, and a test that flips
it must restore it because `cargo test` runs siblings in one process (nextest
does not). [[cite:crates/limedl-native/src/ui_tests/mod.rs:L124-L176]]

`with_ui_async` is the only fixture that drives the runtime (`block_on`) and
Slint's queue. Because the event-loop proxy is process-global, **every**
pump-based scenario lives in the single `event_loop_contracts` test in
`async_contracts/mod.rs`; each scenario is a `pub(super) async fn` grouped by
surface (`bus`, `selection`, `hotkeys`, `rows`, `new_task`, `toolbar`,
`dialogs`) and called from that one `#[test]`. Each scenario builds its own
window with `new_window()` to stay independent, and they advance a shared mocked
clock in 20 ms steps. [[cite:crates/limedl-native/src/ui_tests/mod.rs:L178-L202]]
[[cite:crates/limedl-native/src/ui_tests/async_contracts/mod.rs:L1-L99]]

### TestUi API

`TestUi` wraps the window, the `AppContext` the handlers were registered with,
and the recording core. [[cite:crates/limedl-native/src/ui_tests/mod.rs:L214-L224]]
The core interaction API is `find`, `find_all`, `has`, `click`,
`right_click`, `click_nth`, `right_click_nth`, `shift_click_nth`, `type_text`,
`press_keys`, `search`, `seed` and `visible_rows`.
[[cite:crates/limedl-native/src/ui_tests/mod.rs:L290-L491]]

`shift_click_nth` is the real range gesture: a pointer event carries no modifiers
of its own, so the core fills `PointerEvent.modifiers` from the modifier keys the
window currently sees held down. The helper presses Shift, clicks, then releases
Shift. [[cite:crates/limedl-native/src/ui_tests/mod.rs:L369-L381]]

### Toast assertions

The toast helpers read the Rust-side queue rather than the rendered rows:
`toasts()` returns `(kind, message)` for the pending entries,
`assert_toast(kind, text)` requires exactly one, `toast_ids()` names them for
`dismiss_toast(id)`, which invokes the same callback the close button calls.
[[cite:crates/limedl-native/src/ui_tests/mod.rs:L586-L633]]
Dismissal is a two-stage retire: the entry is marked `leaving` so it stays in
the model for the exit animation, and is dropped only after the animation
window. `toasts()` and `toast_ids()` therefore filter `leaving` out — otherwise
a dismissed toast would still count as pending — and `ui_tests/toast.rs` asserts
both halves: the entry is retired from the pending set and it remains in the
queue during the animation. `sync_toasts`/`apply_toasts` reconciles the model in
place (rows whose id survives are updated, not recreated), so only genuinely
new rows play the enter animation. The reconcile test also queries
`ToastStack::toast_close` to force the stack to lay out, so a binding loop
between the card's height and its layout slot fails the test.
[[cite:crates/limedl-native/src/ui_tests/toast.rs:L1-L135]]
[[cite:crates/limedl-native/src/toast.rs:L39-L59]]

### Window size and geometry

`window_logical_size()` reads the **root element**, not
`Window::size()/scale_factor()`. The testing backend stores whatever size it was
given as physical while reporting the host's scale factor, so
`physical / scale_factor()` is wrong on HiDPI machines. `set_window_size` and
`set_scale_factor` drive the window in logical pixels.
[[cite:crates/limedl-native/src/ui_tests/mod.rs:L427-L459]]

Geometry assertions are `assert_inside_window`, `assert_min_size`,
`assert_no_overlap`, and `bounds`; `assert_inside_window` dumps `id_tree()` on
failure. [[cite:crates/limedl-native/src/ui_tests/mod.rs:L493-L584]]
The testing window defaults to 800x600, so a full-page assertion sets a
larger size first. [[cite:crates/limedl-native/src/ui_tests/updater.rs:L38-L45]]

**Clipped means absent**: element queries skip subtrees that are not visible, and
dialogs are `visible: is_open || opacity > 0.01`, so `has()` doubles as an "is
this dialog actually on screen" check. [[cite:crates/limedl-native/src/ui_tests/mod.rs:L23-L25]]
A control below the fold of a scrolling tab must be scrolled into view first —
`scroll_danger_zone_into_view` dispatches `WindowEvent::PointerScrolled` and
pumps, because the Flickable animates.
[[cite:crates/limedl-native/src/ui_tests/async_contracts/dialogs.rs:L427-L458]]

### The recording backend: assert the blast radius

`RecordingBackend` implements `DownloadBackend` and records every call the UI
makes instead of downloading. [[cite:crates/limedl-native/src/ui_tests/recording.rs:L1-L7]]
It is registered for `TaskKind::Http`, [[cite:crates/limedl-native/src/ui_tests/mod.rs:L255-L257]]
and seeded tasks must use valid UUIDs (`http_task(n, …)`) because `TaskAction`
parses wire ids and silently skips unparseable ones.
[[cite:crates/limedl-native/src/ui_tests/mod.rs:L700-L708]]

- Mutating calls return `NotFound` on purpose, so the *failure* path is reachable
  (the row is dropped optimistically, the backend rejects, the list must
  resynchronize) and no `Updated` event is published behind the test's back.
- `start` is the exception: it returns `Ok` with a synthetic id because the
  success path clears the URL and closes the dialog.

[[cite:crates/limedl-native/src/ui_tests/recording.rs:L66-L82]]
[[cite:crates/limedl-native/src/ui_tests/recording.rs:L287-L305]]

- `starts()` returns the `StartCall` payloads (url, destination dir, file name,
  checksum, expected checksum, selected file indices, headers, user agent and
  mirror urls) — the only way to assert that what the form collected really
  became a `StartDownloadRequest`.
- `settings_pushes()` counts `UpdateSettings` calls, the shared evidence that a
  save from the settings and labs dialogs really reached the backends.

[[cite:crates/limedl-native/src/ui_tests/recording.rs:L22-L39]]
[[cite:crates/limedl-native/src/ui_tests/recording.rs:L110-L129]]

### Click the real widget, type into the real input

Two contract styles decide whether a UI test can actually catch a regression:

- **Click the widget, not the callback.** A `ToggleSwitch` sits three components
  deep (`MainWindow` → `SettingsDialog` → `SettingsTabAppearance`), so the sleep
  inhibition setting is tested by clicking
  `SettingsTabAppearance::prevent_sleep_toggle` and reading the value back out of
  `SettingsFormData` — the only way to prove the whole `<=>` chain carries it,
  since writing the form directly would pass even with a one-way binding. The row
  is below the appearance tab's fold, so the test sets a taller window first (see
  "clipped means absent" above).
  [[cite:crates/limedl-native/src/ui_tests/settings.rs:L272-L302]]
- **Type into the input, then assert the model.** The new-task tests type an
  `aria2c` command into `NewTaskDialog::nt_url_input`, assert the derived fields
  and the hint, and then submit and read the resulting `StartCall` payload
  (mirrors, user agent, digest) — which is what pins parser→dialog→engine wiring
  rather than the parser alone. The batch counter and the long-URL test read the
  dialog's own model (`new_task_batch_count_text`, `assert_inside_window`,
  `has("ScrollView::horizontal-bar")`) instead of re-deriving the expected
  result. [[cite:crates/limedl-native/src/ui_tests/new_task.rs:L162-L257]]
  [[cite:crates/limedl-native/src/ui_tests/async_contracts/new_task.rs:L14-L81]]
  [[cite:crates/limedl-native/src/ui_tests/async_contracts/new_task.rs:L413-L467]]

### Accessibility assertions

`Text` announces its `text` as its accessible label, and the shared
`PrimaryButton`/`SecondaryButton`/`DangerButton` declare
`accessible-role`/label/enabled. Tests assert what the user actually sees with
`ElementHandle::accessible_label()` and `accessible_enabled()` — for example the
updater's phase-to-copy matrix and the enabled state of the check button.
[[cite:crates/limedl-native/src/ui_tests/updater.rs:L22-L90]]

### Pumping

`pump_once` advances the mocked clock by 20 ms, yields the tokio runtime four
times so spawned tasks run, then queues a `quit_event_loop` future and runs
Slint's event loop to drain queued callbacks and due timers. `pump_until`
repeats this against a 5 s wall-clock deadline and waits 1 ms of real time
between rounds with `tokio::time::sleep`, then fails loudly with the recorded
engine calls if the predicate never holds, so a contract that does not settle
fails instead of hanging CI. The real-time yield matters because a pump round
only advances the *mocked* clock while the engine call being waited for can be
blocked on `spawn_blocking` work (`SettingsService` persists through `tokio::fs`);
a counted loop could otherwise exhaust every round before such a task was ever
polled — the settings-save contract did exactly that on a loaded coverage
runner. The wait is an async timer on the real-time current-thread runtime
rather than a blocking `std::thread::sleep`, so the runtime also polls those
spawned completions while the wait is in progress. A fixed-round `pump(n)`
variant exists for contracts whose completion is "no further change".
[[cite:crates/limedl-native/src/ui_tests/mod.rs:L637-L697]]

### Element ids are test contracts

Element lookup needs the debug metadata Slint's compiler embeds on request.
`build.rs` turns it on automatically when `PROFILE=debug` (so `cargo run` and
`cargo test` need no setup) and leaves an explicit `SLINT_EMIT_DEBUG_INFO=1`
alone, which is what lets a `--release` binary be driven by the MCP server.
Without the metadata every id lookup silently matches nothing and prints a
warning instead of failing. Adding a test usually means adding an `id:`
to the `.slint` element, and renaming one is a breaking change for the test that
clicks it. [[cite:crates/limedl-native/build.rs:L84-L106]]

### Known limitations

The testing crate's `internal` feature cannot compile from crates.io (its test
font path only exists in the Slint workspace), so there are no in-process
screenshots; pixels stay on the L2/MCP path.
[[cite:crates/limedl-native/src/ui_tests/mod.rs:L84-L89]]
The main window has no horizontal scroll, so a control clipped at the declared
minimum size is unreachable; layout assertions therefore run at the declared
`min-width`/`min-height` (1100x660), and the optional BT status pills must
collapse *before* they push the toolbar actions past the window edge.
[[cite:crates/limedl-native/src/ui_tests/layout.rs:L27-L34]]
[[cite:crates/limedl-native/src/ui_tests/layout.rs:L113-L127]]

## L2: the MCP server

To let an agent or script open the real window and inspect/click it, the app can
be run with Slint's MCP server instead of a bare `cargo run`. Operational
prerequisites:

- Set `SLINT_EMIT_DEBUG_INFO=1` (for release builds, at **build** time) and
  `SLINT_MCP_PORT=8080` (the command is `cargo run -p limedl-native --features
  slint/mcp`). `build.rs` already embeds the metadata for debug builds, so only
  a release-driven session needs the env var.
  [[cite:docs/manual-smoke-testing.md:L13-L31]] [[cite:AGENTS.md:L21-L23]]
- Quit any running limedl first: the single-instance guard makes a second process
  notify the primary and exit immediately, so the port never opens.
  [[cite:docs/manual-smoke-testing.md:L32-L35]]
- Do **not** pass `--hidden`: the server starts from the "first window shown"
  hook, which never fires on a hidden launch.
  [[cite:docs/manual-smoke-testing.md:L36-L38]]
- Isolate with `LIMEDL_DATA_DIR` and use `SLINT_BACKEND=headless` where there is
  no display (that value only exists with the `mcp` feature compiled in). The
  server binds `127.0.0.1`, has no authentication and validates `Origin`, so it
  is a local development tool.
  [[cite:docs/manual-smoke-testing.md:L39-L45]]
