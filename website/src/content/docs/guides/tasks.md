# 任务管理与并发策略

limedl 摒弃了传统下载器简单盲目设置固定连接数（如粗暴指定 16 或 32 线程）的做法，而是借鉴现代网络拥塞控制理论，设计了高内聚的 **AIMD（Additive Increase Multiplicative Decrease）自适应并发调度引擎**。

---

## 创建下载任务的多种方式

在桌面端日常使用中，你可以通过以下便捷方式快速发起下载：

1. **智能剪贴板监听**：
   复制有效的 HTTP/HTTPS URL 或 `magnet:?xt=urn:btih:` 磁力链接后，切换至 limedl 窗口会自动弹出新建确认框，自动解析文件名与链接类型。
2. **工具栏点击与快捷键**：
   点击主界面顶部工具栏的 **`+ 新建任务`** 按钮，或在主窗口按下 `Ctrl + N`（macOS 上为 `Cmd + N`），粘贴链接并设置目标存储目录。
3. **拖拽导入种子与 Metalink**：
   直接将本地的 `.torrent` 种子文件或 `.metalink` / `.meta4` 多镜像描述文件拖拽入 limedl 窗口任意位置，即可自动解析种子目录树或镜像列表。
4. **浏览器插件一键接管**：
   配合 Chrome / Edge 上的 Aria2 扩展，在网页中点击任何下载链接，浏览器会自动将请求派发至 limedl。
5. **系统命令行调用**：
   通过终端执行 `limedl-native <URL|PATH>`，由单实例机制秒级派发至正在运行的主窗口中。
6. **主动校验和绑定 (Checksum)**：
   在新建任务弹窗中，可直接粘贴文件的预期哈希（支持 Blake3、SHA-256 与 SHA-512，系统会根据哈希长度自动识别算法），下载完成后自动校验。
7. **粘贴 aria2c 命令**：
   新建任务弹窗与剪贴板监听可解析常见 `aria2c` 参数（`-x/--split`、`--header`、`--referer`、`--checksum`、`-d/--dir`、`-o/--out` 等），把现成的命令行直接变成任务。

## HTTP 动态分块引擎工作流程

一个 HTTP 下载任务在 limedl 内部经历严密的五个执行阶段：

```
┌─────────────────┐      HEAD / Range:0-0       ┌───────────────────┐
│ 1. 探测元数据   │ ──────────────────────────► │ 提取 ETag/大小/断点│
└────────┬────────┘                             └─────────┬─────────┘
         │                                                │
         ▼                                                ▼
┌─────────────────┐      根据总大小切片          ┌───────────────────┐
│ 2. 规划 Chunk   │ ──────────────────────────► │ 写入 SQLite 任务库│
└────────┬────────┘                             └─────────┬─────────┘
         │                                                │
         ▼                                                ▼
┌─────────────────┐      JoinSet 异步协程池     ┌───────────────────┐
│ 3. 多流并发拉取 │ ◄─────────────────────────► │ AIMD 动态调速循环 │
└────────┬────────┘                             └─────────┬─────────┘
         │                                                │
         ▼                                                ▼
┌─────────────────┐      落盘缓冲/写合并         ┌───────────────────┐
│ 4. 缓冲池刷盘   │ ──────────────────────────► │ BufferPool 批处理 │
└────────┬────────┘                             └─────────┬─────────┘
         │                                                │
         ▼                                                ▼
┌─────────────────┐      Blake3/SHA-256 哈希    ┌───────────────────┐
│ 5. 校验与最终化 │ ──────────────────────────► │ 原子 Rename 交付  │
└─────────────────┘                             └───────────────────┘
```

### 阶段 1：智能元数据探测 (Probe Phase)
当提交下载链接时，引擎首先向目标 URL 发送轻量级的 `HEAD` 请求（若服务端不支持 HEAD，则平滑回退至 `GET Range: bytes=0-0` 请求）：
- 检测服务端是否支持断点续传（`Accept-Ranges: bytes`）；
- 获取资源总长度（`Content-Length`）；
- 记录资源校验实体标识（`ETag` 与 `Last-Modified`），用于断点续传一致性核验；
- 从 `Content-Disposition` 响应头或 URL 路径中推导并净化目标文件名。

### 阶段 2：动态分块规划 (Chunk Planning)
若服务端支持 Range 请求且文件大于分块阈值，引擎将把文件切分为多个虚拟块（Chunk）：
- **小文件**：采用单流下载并保留断点续传能力；
- **大文件**：根据总长度动态计算最优块尺寸（通常在 2MB ~ 8MB 之间），并构建 `ChunkManifest` 持久化入本地 SQLite 数据库。即使遭遇意外断电，已完成的分块绝不会丢失。

### 阶段 3：AIMD 动态并发调度 (Adaptive Concurrency)
传统固定线程下载有两大弊端：线程过多容易遭遇服务端封禁或触发反爬，线程过少则无法跑满高带宽。

limedl 引入了 **AIMD（加法递增、乘法递减）算法状态机**：
- **加法探测 (Additive Increase)**：
  调度器每隔固定周期（2秒）采样各连接的传输速率与分块完成耗时。若连续几个周期吞吐量保持平稳增长且无连接报错，调度器会逐步向任务追加并发工作连接（+1, +2...），直到达到带宽饱和点。
- **乘法退避 (Multiplicative Decrease)**：
  一旦检测到服务端响应 HTTP 429 (Too Many Requests)、HTTP 503、连接重置或分块读取超时，状态机判定为网络拥塞或服务端限流，按 AIMD 配置**乘法退避**（平衡/激进 ×0.5，保守 ×0.7）并进入冷却期，避免触发服务端永久封禁 IP。
- **镜像故障转移 (Mirror Failover)**：
  当用户为任务配置了多个备用镜像源时，若当前连接源频繁超时，引擎会自动将待下载分块路由至备用镜像，保障下载不掉线。

## Metalink 智能镜像多源下载 (RFC 5854 / RFC 6249)

当通过文件拖拽或 RPC 提交 `.metalink` / `.meta4` 文件时，limedl 会启用内置的 **Metalink 智能调度器**：

- **全协议兼容**：完整支持 Metalink 4.0 XML (RFC 5854)、Metalink 3.0 以及 HTTP 标头 Metalink (RFC 6249 / RFC 3230)；
- **多维度镜像打分 (Mirror Scoring)**：
  系统不会盲目连接单一镜像，而是综合权衡以下维度计算综合优选权重：
  - **显式优先级 (Priority)** 与协议类型（优先 HTTPS）；
  - **地理位置就近度 (Geo Proximity)**；
  - **历史错误惩罚**：连续报错或超时的镜像会被动态降低权重或熔断。

  > 当前版本的打分只使用上述静态属性与历史错误；`MirrorPool` 预留了 RTT 字段，但尚未在下载流程中做主动 RTT 探测。
- **动态镜像租约 (`MirrorPool` & `MirrorLease`)**：
  引擎使用 RAII 模式的 `MirrorLease` 动态分配各镜像的并发连接，并严格限制单一服务器的最大连接数（`max-connection-per-server`），既能跑满多源聚合带宽，又避免打爆镜像服务器引发限流；
- **自动散列与完整性核验**：
  自动读取 Metalink XML 中声明的 Blake3、SHA-256、SHA-512 等哈希签名，下载完成后自动核验，确保跨镜像拼凑数据的百分之百正确。

## 调度模式与并发预算

limedl 提供两种截然不同的调度模式（在 **设置 -> 下载与调度** 中切换）：

### 智能自适应调度 (Automatic Mode) — 默认推荐
- **算法核心**：按**优先级 + 文件总大小**（静态键，不随下载进度变化）确定次序，已运行任务保持线程配额（粘滞）。
- **优势**：大文件优先获得更多线程预算以缩短总体等待时间；高优先级任务可立即抢占；预算不足以覆盖全部任务时，等待最久的任务按固定周期（约 30 秒）轮转进入，既避免尾部任务饥饿，也避免活跃任务被频繁切换。

### 传统队列调度 (Traditional Mode)
- **算法核心**：先按优先级、再按创建时间（同级 FIFO）排序。
- **逻辑**：仅允许最多 `max_parallel_tasks` 个任务处于活跃状态，超出上限的任务在队列中等待；高优先级任务可以排在低优先级任务之前。

## 任务优先级系统

在任务列表或右键菜单中，你可以为任意任务指定优先级：

| 优先级等级 | 调度行为 | 适用场景 |
| :--- | :--- | :--- |
| **高 (High)** | 队列排序优先，预算不足时可抢占低优先级任务的线程 | 急需使用的重要文件、驱动或镜像。 |
| **正常 (Normal)** | 默认顺序，与同级任务按大小/创建时间排序 | 日常下载。 |
| **低 (Low)** | 队列排序靠后，优先作为被抢占者 | 挂机下载的次要资源。 |

优先级不会按固定倍率分配线程，它只影响排序与抢占；实际线程数仍由调度模式和 AIMD 决定。

## 极速滑动窗口速率采样 (SpeedTracker)

limedl 的任务速率监控基于高精度的滑动时间窗口采样器（`SpeedTracker`）：
- 消除瞬时抖动对界面 UI 的剧烈干扰，提供平滑且真实的实时传输速率。
- 动态加权计算精确的预计剩余完成时间（ETA），告别传统计算方式中忽长忽短的估算跳跃。

## 校验和与完整性校验 (Checksums & Integrity)

limedl 支持 Blake3、SHA-256 与 SHA-512。校验来源包括：

- **任务创建时手动指定**：粘贴哈希后按长度自动识别算法；
- **HTTP 响应头**：RFC 3230/9530、S3、GCS 风格的校验和；
- **伴随文件**：`.sha256`、`SHA256SUMS` 等（可在设置中关闭自动识别）；
- **Metalink piece 哈希**：对分块下载逐片校验；发现损坏分片时会重置该分片并把任务标记为失败（可手动恢复/重试）；
- **下载完成后的整文件校验**：按设置或任务指定的算法重新计算。

### 整文件校验失败时的行为

如果最终校验不匹配，limedl **不会**自动推断并只重下“坏块”。当前行为是：

1. 任务标记为 **失败**，错误信息中给出期望值与实际计算值；
2. 临时文件被重命名为 `*.part.corrupt` 保留，便于排查（不会自动删除）；
3. 你可以在任务右键菜单中选择 **校验文件完整性**，对已完成文件（或存在 `.part` / `.part.corrupt` 时）重新计算哈希，并查看进度与结果。

Metalink 的逐片校验是独立的：分片在下载过程中被识别为损坏时会立即重置该分片，任务随后失败；手动恢复/重试时会重新下载该分片，而不是等到整文件校验阶段。
