# Build, Tooling, CI and Release Operations

## Build prerequisites

| Platform | Requirement |
| --- | --- |
| Windows | Initialize MSVC before any Rust command: `vcvarsall.bat x64` [[cite:AGENTS.md:L3-L9]] |
| All | `cargo xtask fetch-font` once (the MiSans VF font is embedded at compile time and is not in git due to its license) [[cite:AGENTS.md:L22-L22]] |
| Linux | `libfontconfig1-dev` (Slint's font stack probes it via pkg-config) [[cite:.github/workflows/ci.yml:L393-L395]] |
| All | `cargo-nextest` pinned to the version CI installs (`nextest@0.9.144`) [[cite:.github/workflows/ci.yml:L403-L405]] |

`.cargo/config.toml` is the single source of truth for target flags: every
`[target.*]` sets `target-cpu=x86-64-v3` for desktop targets (x86-64-v2 for the
NAS musl targets) and adds `--cfg reqwest_unstable`, which reqwest's HTTP/3
feature requires at compile time [[cite:.cargo/config.toml:L1-L42]]. Add both
when introducing a new target. The Linux desktop release reuses
`[target.x86_64-unknown-linux-gnu]` through
`cargo zigbuild --target x86_64-unknown-linux-gnu.2.17`, so the suffixed
cargo-zigbuild target needs no separate entry
[[cite:.cargo/config.toml:L25-L34]].

## xtask tooling

`cargo xtask` is the repository's tooling entry point for release signing, font
fetching, version bumps, multi-hue theme generation, and desktop icon packaging
[[cite:xtask/src/main.rs:L96-L212]]:

| Command | Purpose |
| --- | --- |
| `generate-key --out-dir <dir>` | Create a Minisign keypair and an ML-DSA-65 keypair and print the embedded public-key values (`--pqc-only` rotates just the post-quantum key) |
| `sign <files...>` | Write minisign `<file>.sig` and (when the PQC key is configured) ML-DSA-65 `<file>.pqc.sig` next to each file |
| `verify <files...>` | Verify `.sig` and `.pqc.sig` against a public key |
| `guard <files...>` | Release guard: both signing secrets must match the client's `PUBKEY_B64`/`PQC_PUBKEY_B64` and every signature must verify |
| `manifest --version ...` | Generate the self-update `latest-native.json` |
| `fetch-font [--verify]` | Fetch/verify the pinned MiSans VF font |
| `bump-version <patch\|minor\|major>` | Bump version, update Cargo.lock + website, commit, tag and push |
| `theme generate` | Generate `theme.slint` with 5-hue `ThemeAccent` ramps (token checking lives in `cargo warden slint-theme`) |
| `gen-icons msix\|hicolor\|macos-iconset` | Generate desktop packaging icons |

Static checks and the local pre-commit quality gate are handled by
`cargo-warden` (`cargo warden check` / `cargo warden gate`) configured in
`warden.toml` [[cite:AGENTS.md:L15-L26]] [[cite:warden.toml:L1-L141]].

`bump-version` updates the workspace `Cargo.toml` (first `version = "x.y.z"`),
every `limedl*` workspace package in `Cargo.lock` and the website, then creates
a `chore: bump version to X` commit and pushes commit + tag; `--dry-run` prints
the plan and `--no-push` skips git [[cite:xtask/src/bump_version.rs:L57-L151]].

The lock rewrite matches the whole `limedl*` class instead of a hard-coded list
of crate names, and its result is re-checked: if any `limedl*` lock entry still
lags, the bump fails *before* committing or tagging
[[cite:xtask/src/bump_version.rs:L82-L107]]. The code comment states the reason
structurally: the open suffix class means a newly added workspace crate cannot
be forgotten, and a miss is fatal here instead of at a tagged release whose
`cargo zigbuild --locked` legs refuse to update the lock file and fail minutes
into every server/image job. A workspace crate the rewrite cannot express now
fails loudly at the same point. `xtask` is unaffected: it pins its own literal
`0.0.0` [[cite:xtask/Cargo.toml:L1-L3]].

## The font artifact flow

`MiSansVF.ttf` is embedded into the `limedl-native` binary at compile time and
**cannot be committed** — the MiSans license forbids redistributing the file,
only works that embed it
[[cite:.github/actions/fetch-misans/action.yml:L1-L15]].
`cargo xtask fetch-font` downloads it from Xiaomi's CDN, pinned by size
(`20_093_424`) and SHA-256 (`0ddef906…a115e79`), with a transport ladder
(`--http2` → `--http1.1` → `--http1.1 --ipv4`), chunked range fetch and escape
hatches (`LIMEDL_MISANS_TTF`, `--from-path`, `--zip-url`, `--verify`)
[[cite:xtask/src/fetch_font.rs:L5-L57]].

In CI the `font` job fetches it once and publishes the `misans-vf` artifact;
every job that compiles the UI crate restores that artifact and runs
`fetch-font --verify` instead of hitting the CDN
[[cite:.github/workflows/ci.yml:L111-L143]]. This exists because a cold cache
previously meant four runners downloading from Xiaomi simultaneously, so a CDN
hiccup read as four unrelated failures
[[cite:.github/workflows/ci.yml:L111-L121]]. The headless server needs no font —
its release job does not even take the `font` job as a dependency
[[cite:.github/workflows/release.yml:L551-L554]].

## The mandatory pre-commit gate

CI fails on any test failure, warning or error regardless of whether a given
diff caused it, so the same gate must be green locally before committing
[[cite:AGENTS.md:L115-L118]]. The gate is driven by `cargo-warden` using
`warden.toml`: `cargo warden check` runs the fast static checks (`dag`,
`ci-parity`, `slint-theme`, `i18n`, `complexity`, `file-length` against
`warden-baseline.json`), and `cargo warden gate` adds `fmt`, `clippy`, `doc` and
all test suites, mirroring the order CI runs them
[[cite:AGENTS.md:L122-L130]] [[cite:warden.toml:L53-L106]].

The design points that matter:

- The package list comes from `cargo metadata`; `test_groups` in `warden.toml`
  must cover every workspace member, and `cargo warden ci-parity` re-reads
  `ci.yml` and fails when a member's tests or coverage fan-out entries are
  missing [[cite:warden.toml:L9-L14]] [[cite:warden.toml:L77-L106]]. This is
  what prevents `--manifest-path crates/limedl-core/Cargo.toml` from silently
  skipping sibling suites (269 tests once vanished when `limedl-types` and
  `limedl-disk` were split out) [[cite:AGENTS.md:L132-L138]]. In CI the engine
  and RPC crates are selected together on one `nextest` line with the
  `limedl-core/test-utils` feature, and `xtask`, `limedl-native` and
  `limedl-server` run as their own steps [[cite:.github/workflows/ci.yml:L242-L248]].
- CI's environment is applied by the gate (`CARGO_BUILD_WARNINGS=deny`) and the
  rustfmt pin (`1.99.0`) is checked [[cite:AGENTS.md:L139-L141]]
  [[cite:warden.toml:L72-L75]]. Warnings are fatal through
  `CARGO_BUILD_WARNINGS=deny` (cargo's own `build.warnings`, orthogonal to
  RUSTFLAGS) plus clippy's `-- -D warnings`, deliberately **not**
  `RUSTFLAGS="-D warnings"`, which would override `.cargo/config.toml`'s
  per-target flags [[cite:.github/workflows/ci.yml:L75-L84]].
- `cargo doc` runs with `RUSTDOCFLAGS=-D warnings`, because clippy never
  resolves doc links and a doc comment pointing at a module that moved to
  another crate would otherwise stay green forever
  [[cite:AGENTS.md:L142-L147]].
- `cargo warden gate --full` is the CI-parity profile: it adds the custom
  feature-matrix steps (`hack-core`, `hack-types`), unused-deps check
  (`cargo machete`), license gate (`cargo deny`) and RustSec audit
  (`cargo audit`) — the last three live in the `supply-chain` CI job
  [[cite:AGENTS.md:L150-L153]] [[cite:warden.toml:L107-L141]].
- Existing complexity (`> 25`) and physical file-length (`> 800`) violations are
  captured in `warden-baseline.json` so only regressions fail `cargo warden
  check` [[cite:warden.toml:L3-L64]] [[cite:AGENTS.md:L171-L173]].
- CI does not call `cargo warden gate` directly. `ci.yml` is the authority; the
  `gate-contract` job (`Warden (Linux, checks & CI parity)`) downloads the pinned
  `cargo-warden` release binary (`v0.2.0`, SHA256-verified) and runs
  `cargo warden check` (including `ci-parity`) to keep `warden.toml` and `ci.yml`
  in sync [[cite:AGENTS.md:L154-L156]] [[cite:.github/workflows/ci.yml:L626-L657]].
- `cargo nextest run` does not execute doctests; the workspace has none, and
  adding one requires a matching `cargo test --doc` step in CI
  [[cite:.github/workflows/ci.yml:L104-L106]].

Coverage is a hard gate in CI: `cargo llvm-cov nextest` on the engine crates
with `--fail-under-lines 85`
[[cite:.github/workflows/ci.yml:L447-L477]]. The tool is pinned to
`cargo-llvm-cov@0.9.0` because the 0.6 → 0.9 change to instrumentation moved
the denominator; re-baselining needs a clean run with the pinned tool
[[cite:.github/workflows/ci.yml:L396-L402]],
[[cite:.github/workflows/ci.yml:L452-L463]]. `cargo-llvm-cov` ignores `tests/`
directories and `tests.rs`/`*_tests.rs` files, so the metric is product code
[[cite:.github/workflows/ci.yml:L447-L450]]. A second lcov is generated for
`limedl-native` with `--ignore-filename-regex` (to keep the engine's lines out
of the native report) and `--no-cfg-coverage` (the latter because `tiny-xlib`
turns `cfg(coverage)` into a nightly-only feature under stable)
[[cite:.github/workflows/ci.yml:L488-L508]]. `limedl-server` and `xtask` have no
lcov report and are excluded from the Sonar coverage metric instead of being
counted as 0% [[cite:sonar-project.properties:L47-L58]],
[[cite:sonar-project.properties:L84-L84]].

### The gate cannot see non-Windows code from Windows

On a Windows host, `cfg(not(windows))` items are never compiled, so
`cargo clippy --workspace --all-targets` misses unused imports/types/statics
that only macOS and Linux reach, a `build.rs` dependency or feature only
required off Windows (`rfd`'s `xdg-portal` needs `tokio` or `async-std`), and a
`-l<lib>` whose `-dev` package is missing [[cite:AGENTS.md:L178-L185]].

Mitigations: prefer `#[cfg]` over runtime `CARGO_CFG_TARGET_OS` checks in
`build.rs` and `platform_*.rs` so dead code is not compiled everywhere; treat a
tagged release as the first real platform check and publish only after
`check-macos` / `check-rust` are green on that commit; when adding a
platform-gated module, re-read it asking "what does this file look like with
`cfg(windows)` false?" [[cite:AGENTS.md:L187-L196]]. The `sign-check` workflow
and the macOS linker-warning exemption are covered below and in the release
page.

## CI job graph

`.github/workflows/ci.yml` runs these jobs
[[cite:.github/workflows/ci.yml:L109-L802]]:

| Job | Platform | What it runs |
| --- | --- | --- |
| `font` | Linux | Fetch MiSans VF once, upload `misans-vf` |
| `check-windows` | Windows | `cargo clippy --workspace --all-targets -- -D warnings` |
| `test-windows-core` | Windows | nextest for the engine crates (with features) and `xtask` |
| `test-windows-native` | Windows | nextest for `limedl-native` |
| `check-macos` | macOS | clippy → engine nextest → native nextest |
| `check-rust` | Linux | coverage (engine + native lcov) → fmt check → clippy → cargo doc → feature matrix → SonarCloud → native nextest → `limedl-server` nextest |
| `gate-contract` | Linux | `cargo warden check` (static checks + CI/gate parity) |
| `wiki` | Linux | `loredex lint`, `loredex check --mark`, `loredex agents-md --check` |
| `supply-chain` | Linux | `cargo deny check -W rejected bans licenses sources`, `cargo audit`, `cargo machete --with-metadata` |
| `prune-cache` | Linux | main-only GC of superseded `v0-rust-*` cache generations; `needs` the three rust-cache writers |

`prune-cache` is a bookkeeping job, not a test: it runs after
`test-windows-native`, `check-macos` and `check-rust` (with `always()`, so a
failed writer still leaves the previous generation as the newest per prefix) and
deletes every cache entry older than the newest for its key prefix
[[cite:.github/workflows/ci.yml:L754-L802]]. It is the only job that asks for
`actions: write`, scoped to the job rather than the workflow
[[cite:.github/workflows/ci.yml:L761-L763]].

`limedl-server` is exercised **only** on the Linux leg. Its end-to-end test
binds a real port and bootstraps the engine, so running it on the Windows/macOS
legs would add flake for a daemon that targets musl Linux; those legs still
*compile* it through `cargo clippy --workspace --all-targets`
[[cite:.github/workflows/ci.yml:L587-L594]].

A separate `.github/workflows/aria2-oracle.yml` runs the Tier 2 aria2 oracle
(`crates/limedl-rpc/src/oracle_tests.rs`) on a nightly `schedule` and on
`workflow_dispatch` — never on push or pull request. It is a standalone workflow
rather than a `ci.yml` job on purpose: a `schedule` on `ci.yml` would run the
whole Windows/macOS/Linux matrix nightly, and the oracle needs a third-party
`aria2` binary whose output drifts with its release
[[cite:.github/workflows/aria2-oracle.yml:L1-L22]]. It is a **reader** of the
Linux `ci-debug` cache entry (`save-if: false`), so it reuses `check-rust`'s
artifacts instead of a cold build [[cite:.github/workflows/aria2-oracle.yml:L45-L51]].
The oracle asserts the client-facing contract against allowlists (AriaNg option
keys, always-present `tellStatus` keys, the documented
`listMethods`/`listNotifications` delta, code 1 error objects and JSON-RPC
batch); it fails on anything outside them, when the oracle cannot start, or when
a server stops answering, and the remaining aria2-only differences are printed
as allowlisted notes [[cite:.github/workflows/aria2-oracle.yml:L12-L17]],
[[cite:crates/limedl-rpc/src/oracle_tests.rs:L1-L52]].

Windows is split into three parallel jobs because its native job is the critical
path and clippy is check-only and cannot share build artifacts with the test
builds [[cite:.github/workflows/ci.yml:L145-L162]].

### Cache and RUSTFLAGS contract

Every job passes `cache: false` to `actions-rust-lang/setup-rust-toolchain`
(because it runs rust-cache internally) and then runs `swatinem/rust-cache`
explicitly exactly once [[cite:.github/workflows/ci.yml:L29-L37]]. The Rust jobs
share one `ci-debug` key per OS via `shared-key`; rust-cache still appends the
runner OS/arch, so Windows, Linux and macOS stay separate
[[cite:.github/workflows/ci.yml:L48-L50]].

**Key shape.** `v0-rust-<shared-key>-<os>-<arch>-<envHash>-<lockHash>`
[[cite:docs/ci-operations.md:L39-L46]]:

- `envHash` covers the installed Rust toolchain versions plus every
  `RUST*`/`CARGO*`/`CC*`/`CFLAGS*`/`CXX*`/`CMAKE*` environment variable present
  on the cache step, and **does not include source**. A job-scoped variable such
  as `CARGO_BUILD_WARNINGS` is therefore part of the key, which is why such
  variables belong on the steps that need them when key sharing matters
  [[cite:docs/ci-operations.md:L39-L46]],
  [[cite:docs/ci-operations.md:L123-L128]].
- `lockHash` hashes each workspace member's `Cargo.toml` with `package.version`
  normalised to `0.0.0` and path dependencies blanked, the external packages of
  `Cargo.lock` (parsed, not read as bytes), and the **raw bytes** of
  `.cargo/config.toml` / `rust-toolchain*`. Two consequences: a version bump does
  not invalidate the cache, and a Windows CRLF checkout gives Windows a different
  `lockHash` than Linux/macOS on the same commit (measured `75a17e6d` vs
  `73b11a8a`, run 37568494078) — harmless while each OS keeps its own entries,
  but it rules out cross-OS key equality
  [[cite:docs/ci-operations.md:L43-L56]].
- rust-cache caches dependency artifacts only. In `check-rust` that includes the
  instrumented `target/llvm-cov-target` tree that `cargo llvm-cov` writes
  *under* `target/`, which is why the Linux entry is the largest (2917 MiB vs
  1197 MiB on Windows and 1660 MiB on macOS)
  [[cite:docs/ci-operations.md:L76-L79]].

**Restore semantics.** A full key match is not written back. When only the
prefix matches (`restoreKey` = key minus `lockHash`), rust-cache restores the
previous generation, keeps its dependency artifacts, and writes a new generation
under the new `lockHash` — so a lockfile bump is an incremental rebuild, not a
cold one [[cite:docs/ci-operations.md:L48-L58]].

Additional rules:

- **Exactly one writer per shared key** (`test-windows-native` for Windows,
  `check-rust` for Linux, `check-macos` for macOS), gated on
  `github.ref == 'refs/heads/main'`; everyone else passes `save-if: false`.
  Multiple writers race after a lockfile bump and recreate duplicate entries,
  which pushed the repo to 11.7 GB against GitHub's 10 GB ceiling and caused LRU
  eviction of the Linux caches [[cite:docs/ci-operations.md:L107-L122]].
- Every writer also passes **`cache-on-failure: true`**. The action's post step
  is gated on `success() || CACHE_ON_FAILURE == 'true'`; without it a run that
  changes the lockfile and then fails a test pays the save twice (once red, once
  on the fix). The Windows save measured 127-179 s for ~1.2 GB, and a failing
  test does not invalidate dependency artifacts
  [[cite:docs/ci-operations.md:L59-L64]].
- **Superseded generations are collected by the `prune-cache` job** (main-only,
  `needs` the three writers with `always()`). Each lockfile change otherwise
  leaves the previous generation until GitHub's repository-wide LRU reclaims it.
  The job keeps only the most recently created entry per key prefix — the only
  entry a bare prefix restore can ever pick — and deletes the rest through the
  GitHub caches REST endpoint (`gh api repos/$REPO/actions/caches`). Two
  invariants keep it safe: it never deletes the newest entry per prefix, and it
  never selects outside `v0-rust-`, so the rolling `Linux-sonar` and `misans-vf`
  caches keep their own lifecycle. Measured 2026-10-07 before it existed: 5
  `v0-rust-*` entries / 8.54 GB, of which 2.73 GB were superseded
  [[cite:docs/ci-operations.md:L65-L75]].
- `rustflags: ""` leaves RUSTFLAGS unset so `.cargo/config.toml` stays
  authoritative [[cite:.github/workflows/ci.yml:L75-L77]].
- Windows jobs exclude build paths from Defender real-time scanning
  (best-effort), which is the dominant Windows-vs-Linux build penalty
  [[cite:.github/workflows/ci.yml:L91-L96]].
- The Linux entry's size is **measured, not gated**. The recorded decision
  (2026-10-13) is that pointing `CARGO_LLVM_COV_TARGET_DIR` /
  `CARGO_LLVM_COV_BUILD_DIR` at `target/` would *move* the coverage dev rlibs
  into `target/debug` rather than remove bytes — `cargo llvm-cov` runs with
  `--cargo-profile dev` while the other nextest steps use the default `test`
  profile, so the two trees are not duplicates — at the cost of a full dev
  rebuild; it was rejected. The remaining size lever (running the native/server
  nextest steps with `--cargo-profile dev`) trades away `[profile.test] debug =
  false` and runs instrumented test binaries, so it stays closed without new
  measurements [[cite:docs/ci-operations.md:L76-L96]].

## Release pipeline

Pushing a `v*` tag triggers `.github/workflows/release.yml`
[[cite:.github/workflows/release.yml:L32-L34]]:

1. `font` fetches the font once [[cite:.github/workflows/release.yml:L40-L70]].
2. `changelog` computes the previous tag and generates the release body with
   **git-cliff** (`cliff.toml`) from Conventional Commits. `test:`, `ci:`,
   `chore:`, `build:` and `style:` are omitted from the notes;
   `feat:`/`fix:`/`perf:`/`refactor:`/`docs:` are grouped
   [[cite:.github/workflows/release.yml:L77-L121]],
   [[cite:cliff.toml:L32-L47]]. Keep commit subjects Conventional so notes stay
   readable.
3. `build-native` (Windows), `build-native-macos` and `build-native-linux` build
   and package their artifacts [[cite:.github/workflows/release.yml:L129-L132]],
   [[cite:.github/workflows/release.yml:L332-L335]],
   [[cite:.github/workflows/release.yml:L421-L424]]. The Linux leg builds with
   `cargo zigbuild --target x86_64-unknown-linux-gnu.2.17` and runs
   `scripts/check-glibc-floor.sh --max 2.17`, so the portable/deb/AppImage keep
   a glibc 2.17 floor instead of the runner's 2.39 while still linking the
   distro's dynamic system libraries
   [[cite:.github/workflows/release.yml:L473-L482]]. All three legs upload to
   the release.
4. `build-server` cross-compiles the headless `limedl-server` for
   `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` with
   `cargo zigbuild` (zig bundles the musl C toolchain `aws-lc-sys` needs, so no
   Docker image is required) and uploads tarballs that also contain the systemd
   unit and env example [[cite:.github/workflows/release.yml:L532-L546]],
   [[cite:.github/workflows/release.yml:L597-L612]]. They are not signed, not
   guarded and not part of `latest-native.json`
   [[cite:.github/workflows/release.yml:L548-L549]].
5. `server-image` assembles those same prebuilt static binaries into a thin
   Alpine image (no engine rebuild), pushes one image per architecture, and
   merges them into a multi-arch `ghcr.io/zkz098/limedl-server` manifest
   [[cite:.github/workflows/release.yml:L631-L644]],
   [[cite:.github/workflows/release.yml:L683-L719]]. The `latest` tag is skipped
   for an alpha/beta/rc release [[cite:.github/workflows/release.yml:L711-L715]].
   QEMU is used only for the image's Alpine `apk add` layer
   [[cite:.github/workflows/release.yml:L640-L642]].
6. `native-manifest` is the **sole writer** of `latest-native.json`: it runs
   with `if: always()`, merges only the platform legs that succeeded, dual-signs
   every artifact (Minisign + ML-DSA-65), generates and dual-signs the manifest,
   and runs `cargo xtask guard`
   [[cite:.github/workflows/release.yml:L721-L743]],
   [[cite:.github/workflows/release.yml:L791-L859]]. A missing platform key is
   handled by the client as "no update" instead of an error
   [[cite:.github/workflows/release.yml:L730-L733]]. It lists `build-server` in
   `needs` only so it flips the release's `prerelease` flag to `false` last
   [[cite:.github/workflows/release.yml:L735-L737]],
   [[cite:.github/workflows/release.yml:L861-L879]].

Both `cargo zigbuild` legs install Zig from the PyPI `ziglang` wheel pinned to
`0.16.0` and pass `pip --only-binary ":all:"`; the wheel ships no `zig` console
script, so the packaged binary is symlinked onto `PATH` for cargo-zigbuild
[[cite:.github/workflows/release.yml:L460-L470]],
[[cite:.github/workflows/release.yml:L584-L591]].

The signing keys never appear in the tree; `cargo xtask guard` fails the release
if either CI secret's derived public key does not match the client's
`PUBKEY_B64`/`PQC_PUBKEY_B64` [[cite:.github/workflows/release.yml:L785-L790]].

The `Signing check` workflow is the manual counterpart: it signs a throwaway
file and runs `guard` without publishing, so a rotation of either the Minisign
or the ML-DSA-65 key can be validated on demand
[[cite:.github/workflows/sign-check.yml:L1-L48]].

### The Linux glibc floor

Lowering the desktop Linux floor is a release concern of its own, because the
Slint build cannot be static (fontconfig is a direct `DT_NEEDED` and
X11/Wayland/GL are loaded at runtime), so musl is not an option
[[cite:.github/workflows/release.yml:L399-L411]]. `cargo zigbuild --target
x86_64-unknown-linux-gnu.2.17` keeps the binary dynamically linked but makes the
linker resolve its *own* libc references against glibc 2.17 — Rust's minimum for
the gnu target [[cite:.github/workflows/release.yml:L402-L410]].
`scripts/check-glibc-floor.sh` reads the ELF's `GLIBC_*` symbol versions with
`objdump` and fails the release if any exceeds 2.17, so a future dependency
cannot silently raise the floor again
[[cite:scripts/check-glibc-floor.sh:L1-L60]].

## Dependency discipline

After `cargo update` / `cargo add` / `cargo remove`, commit the changed
`Cargo.lock`. Uncommitted lockfile changes cause CI cache misses and stale
dependency resolution [[cite:AGENTS.md:L198-L202]].

The BitTorrent engine is a workspace dependency (`librqbit 9.1`, default features
off, `rust-tls` on), and `limedl-bt` is the only crate that names it — the
engine-wide dependency table keeps the rest of the graph free of it
[[cite:Cargo.toml:L84-L85]], [[cite:crates/limedl-bt/Cargo.toml:L13-L23]].
