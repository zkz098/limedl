# Metalink 与镜像选择

当一个文件有多个下载源时，limedl 可以按 Metalink 描述动态分配连接、隔离坏镜像，并在下载完成后按声明的哈希校验。本文说明实际支持的格式、镜像选择规则与已知边界。

---

## 支持的输入

| 来源 | 使用方式 |
| :--- | :--- |
| `.metalink` / `.meta4` 文件 | 直接拖入窗口，或作为本地任务提交 |
| Metalink 4.0 XML（RFC 5854） | `aria2.addMetalink` 上传 base64 编码的 XML |
| Metalink 3.0 | 同上 |
| HTTP `Link` 头（RFC 6249） | 服务器返回 `rel="duplicate"`、`rel="describedby"`、`Digest` 时自动识别 |
| 普通镜像列表 | 任务带 `mirror_urls` 时也会建立镜像池 |

:::note[解析边界]
- Metalink XML 超过 **10 MiB** 会被直接拒绝。
- 文档中没有 `<file>` 条目会作为错误处理，而不是“空成功”。
- 文件名只保留 basename 并做安全化处理，避免写出目标目录。
- 只有 **SHA-512 / SHA-256 / BLAKE3** 会被识别为有效校验算法；其他算法按“无校验”处理。
:::

## 镜像如何排序

引擎为每个镜像维护综合分数，主要因素：

| 因素 | 作用 |
| :--- | :--- |
| `<url priority>` | RFC 5854 语义：**1 最高**，数值越大越靠后 |
| 协议 | HTTPS 优先 |
| 地理位置 | 配置了偏好地区时，同地区 / 邻近地区加分 |
| 连续错误 | 每次失败降低分数并进入指数退避 |
| RTT | 镜像池的评分函数支持 RTT，但当前下载流程从 URL 列表建池时**没有执行主动 RTT 探测**；实际排序主要依赖优先级、协议、地区与错误历史 |

因此，“多镜像”不等于“自动测速排名”：它更像一个带健康状态的优先级池。需要真实吞吐测速时，请使用[CDN 探针](/guides/cdn/)。

## 租约、冷却与故障隔离

- **动态租约**：每个工作线程向 `MirrorPool` 申请一个镜像租约，租约归还前占用该镜像的并发名额。
- **每镜像连接上限**：达到 `max-connections` 的镜像不会被继续租用；所有镜像都满时，退回到活跃连接最少的镜像。
- **失败退避**：连续失败按 `2^errors` 秒退避（上限 60 秒），冷却中的镜像被跳过。
- **坏分片隔离**：某个镜像返回的分片校验失败时，会额外记 5 次错误并隔离约 300 秒，避免继续从同一源拉取损坏数据。
- **RAII 租约**：工作线程提前返回或出错时，镜像并发名额会自动释放，不会泄漏。

## 校验与失败行为

- 整文件优先使用 **SHA-512 > SHA-256 > BLAKE3**。
- Metalink 的 `<pieces>` 会启用逐片校验：分片损坏时立即重置该分片，任务随后失败，手动恢复/重试会重新下载该分片。
- 普通整文件校验失败时，任务标记为失败，临时文件保留为 `*.part.corrupt`；limedl **不会**自动推断并只重下坏块。
- 右键菜单的“校验文件完整性”可以对已完成文件或 `.part` / `.part.corrupt` 重新计算哈希。

---

## 使用建议

1. **优先使用官方 Metalink**，不要手工拼来源不明的镜像列表。
2. 声明了分片/整文件哈希时，镜像返回 HTML 错误页会导致校验失败；分片错误还会隔离该镜像。**没有声明哈希时，limedl 无法识别 200 状态的错误页**，也不会凭空判断内容是否正确。
3. 需要“哪个镜像更快”的实测结果时，先通过 CDN 探针或 URL 重写选出快源，再交给 Metalink 做多源聚合。
4. 通过 Aria2 RPC 提交时，`select-file` 是 **1 起始**的逗号分隔文件索引，适用于包含多个文件的 Metalink。

---

## 已知边界

- 当前评分没有把实时 RTT 探测接入下载流程；`probe_mirrors` 是库组件，尚未在调度路径调用。
- 镜像地理位置来自 Metalink 元数据；元数据缺失时不会凭空推断。
- 镜像内容一致性由哈希保证；如果 Metalink 本身没有声明哈希，limedl 无法判断镜像是否被篡改。
